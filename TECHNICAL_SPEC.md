## Data Structures

### Transaction

```cpp
struct Transaction {
    uint32_t txId;           // Unique transaction identifier
    uint32_t sourceNodeId;   // Node that created the transaction
    double timestamp;        // Creation time (simulation time)
    std::string data;        // Payload (CAM/DENM message)
    double delay;            // Network delay for QoI filtering
};
```

**Size**: ~64 bytes (estimated)

**Lifecycle**:
1. Generated by NodeApp
2. Added to pending transaction pool
3. Filtered by QoI (delay threshold)
4. Included in block candidate
5. Validated by consensus
6. Committed to blockchain

### BlockCandidate

```cpp
struct BlockCandidate {
    uint32_t blockId;                    // Unique block identifier
    uint32_t proposerNodeId;             // Node proposing the block
    std::vector<Transaction> transactions; // Block payload
    double timestamp;                    // Block creation time
    std::string consensusType;           // "PoW", "PoS", or "FBA"
    uint32_t difficulty;                 // PoW difficulty level
    std::string previousBlockHash;       // Link to previous block
    std::string blockHash;               // Block identifier/signature
};
```

**Size**: Variable, ~640 bytes for 10 transactions

**Validation Rules**:
- Must reference valid previous block
- Transactions must pass QoI filtering
- Hash/signature must be valid for consensus type
- Block size must not exceed maximum

## Algorithms

### Informational Entropy Calculation

**Purpose**: Measure disorder in transaction distribution

**Algorithm**:
```
Input: nodeStates (map of node ID -> NodeState)
Output: S (informational entropy)

1. totalTxs = 0
2. For each node in nodeStates:
      totalTxs += node.pendingTxs.size()

3. If totalTxs == 0:
      return 0

4. S = 0
5. For each node in nodeStates:
      if node.pendingTxs.size() > 0:
          p_i = node.pendingTxs.size() / totalTxs
          S -= p_i * log2(p_i)

6. Return S
```

**Properties**:
- Range: [0, log₂(N)] where N is number of nodes
- S = 0: All transactions at one node (perfect order)
- S = log₂(N): Perfectly distributed (maximum disorder)
- Threshold: 0.5 (empirically determined for V2X)

**Complexity**: O(N) where N is number of nodes

### Spatial Entropy Calculation

**Purpose**: Measure vehicle dispersion in physical space

**Algorithm**:
```
Input: nodeStates, gridSize (default 100m)
Output: H_spatial

1. Create empty grid map

2. For each node in nodeStates:
      pos = node.position
      gridX = floor(pos.x / gridSize)
      gridY = floor(pos.y / gridSize)
      grid[(gridX, gridY)]++

3. totalNodes = nodeStates.size()
4. H_spatial = 0

5. For each cell in grid:
      p_i = cell.count / totalNodes
      H_spatial -= p_i * log2(p_i)

6. Return H_spatial
```

**Properties**:
- Range: [0, log₂(C)] where C is number of grid cells
- H = 0: All vehicles in one cell (clustered)
- H = log₂(C): Perfectly dispersed
- Threshold: 0.6 (empirically determined)

**Grid Size Impact**:
- Larger grid: Coarser granularity, lower entropy
- Smaller grid: Finer granularity, higher entropy
- Default: 100m (suitable for urban V2X range)

**Complexity**: O(N) where N is number of nodes

### Consensus Mode Decision

**Purpose**: Select appropriate consensus mechanism

**Algorithm**:
```
Input: S (informational entropy), H (spatial entropy)
Output: mode (LOW_COST or HIGH_RIGOR)

if (S > S_th) OR (H > H_th):
    return HIGH_RIGOR  // Use PoS or FBA
else:
    return LOW_COST    // Use PoW
```

**Thresholds**:
- S_th = 0.5: Informational entropy threshold
- H_th = 0.6: Spatial entropy threshold

**Rationale**:
- High entropy → Network disorder → Need faster consensus → HIGH_RIGOR
- Low entropy → Network stable → Can afford slower mining → LOW_COST
- OR operator: Either condition triggers HIGH_RIGOR (conservative)

### QoI Filtering

**Purpose**: Discard stale transactions

**Algorithm**:
```
Input: transactions, delayThreshold (default 0.5s)
Output: filteredTransactions

currentTime = Simulator::Now()
filteredTransactions = []

For each tx in transactions:
    delay = currentTime - tx.timestamp
    if delay <= delayThreshold:
        filteredTransactions.append(tx)

Return filteredTransactions
```

**Impact**:
- Reduces blockchain bloat
- Improves information freshness
- Essential for safety-critical V2X applications

## Energy Models

### Radio Energy

**Model**: NS-3 WifiRadioEnergyModel

**Parameters**:
- TX Current: 17.4 mA
- RX Current: 19.7 mA
- Idle Current: ~0 mA (assumed)
- Voltage: 3.3V (typical)

**Calculation**:
```
E_radio = (I_tx * t_tx + I_rx * t_rx) * V
```

**Measurement**: Integrated automatically by NS-3

### Cryptographic Energy

**PoW Model**:
```
E_crypto = e_h × n_hash
```

Where:
- e_h = 5 μJ/hash (based on SHA-256 hardware)
- n_hash ~ Exponential(λ = 1/2^D)
- D = difficulty level (default: 4)

**Average Energy**:
```
E_avg = e_h × 2^D
     = 5 μJ × 2^4
     = 80 μJ per block
```

**PoS/FBA Model**:
```
E_crypto = e_sig × n_sig
```

Where:
- e_sig = 1 μJ/signature (based on ECDSA)
- n_sig = 1 (PoS) or quorum_size (FBA)

**Typical Energy**:
- PoS: ~1 μJ per block
- FBA: ~10 μJ per block (10 quorum members)

**Trade-off**:
- PoW: High energy, high security, slow
- PoS: Low energy, moderate security, fast
- FBA: Moderate energy, high security, fast

## Performance Characteristics

### Latency

**Target**: Sub-100 ms block generation

**Actual Performance**:

| Mode | Mean Latency | 95th Percentile |
|------|--------------|-----------------|
| LOW_COST (PoW) | 5-50 ms | 80 ms |
| HIGH_RIGOR (PoS) | 1-5 ms | 10 ms |
| HIGH_RIGOR (FBA) | 5-15 ms | 30 ms |

**Factors**:
- PoW: Dependent on difficulty and hash rate
- PoS: Minimal computation, mainly signature
- FBA: Network round-trips for quorum agreement

### Throughput

**Block Size**: 10 transactions (default)

**Block Interval**: Variable, depends on:
- Transaction arrival rate
- Control loop frequency (1 second default)
- Consensus latency

**Estimated Throughput**:
- Best case: 10 tx/s (block every second)
- Typical: 5-8 tx/s
- Worst case: 1-2 tx/s (under high load)

**Comparison to V2X Requirements**:
- CAM frequency: 10 Hz (per vehicle)
- For 50 vehicles: 500 messages/s required
- Current throughput: 5-10 tx/s (sufficient for aggregated safety messages)

### Scalability

**Node Scaling**:

| Nodes | S (avg) | H (avg) | Mode Switches/min |
|-------|---------|---------|-------------------|
| 10 | 0.2-0.3 | 0.3-0.4 | 1-2 |
| 50 | 0.4-0.6 | 0.5-0.7 | 5-10 |
| 100 | 0.6-0.8 | 0.7-0.9 | 15-25 |

**Observations**:
- Entropy increases with node count
- More nodes → More HIGH_RIGOR mode usage
- Switching frequency increases non-linearly

## Security Considerations

### Fork Resistance

**Mechanism**: Longest chain rule (implicit in commit logic)

**Risk Factors**:
- Network partitions (can cause temporary forks)
- Byzantine nodes (< 33% for FBA)
- Selfish mining (mitigated by adaptive switching)

**Mitigation**:
- HIGH_RIGOR mode during high entropy (less fork-prone)
- QoI filtering reduces invalid transactions
- Quorum-based agreement in FBA

### Attack Vectors

1. **Sybil Attack**: Multiple fake identities
   - Mitigation: PoS stake requirement, FBA trusted quorum

2. **51% Attack**: Majority hash power (PoW)
   - Mitigation: Switch to PoS/FBA under attack conditions

3. **Double Spending**: Same transaction in multiple blocks
   - Mitigation: Transaction ID uniqueness check

4. **DoS Attack**: Flood with invalid transactions
   - Mitigation: QoI filtering, rate limiting

## Configuration Parameters

### Critical Parameters

| Parameter | Default | Range | Impact |
|-----------|---------|-------|--------|
| S_th | 0.5 | 0.0-2.0 | Higher → Less HIGH_RIGOR |
| H_th | 0.6 | 0.0-2.0 | Higher → Less HIGH_RIGOR |
| Block Size | 10 | 1-100 | Higher → Less blocks |
| Beacon Interval | 0.1s | 0.01-1.0s | Lower → More messages |
| QoI Threshold | 0.5s | 0.1-5.0s | Lower → More filtering |

### Tuning Guidelines

**Urban Scenario**:
- Lower S_th (0.4-0.5): More vehicles, higher entropy
- Moderate H_th (0.5-0.7): Clustered around intersections
- Smaller blocks (5-10): Faster commits

**Highway Scenario**:
- Higher S_th (0.6-0.7): Linear arrangement
- Lower H_th (0.4-0.5): Spread along highway
- Larger blocks (10-20): More consistent traffic

**Emergency Scenario**:
- Very low thresholds (0.2-0.3): Always HIGH_RIGOR
- Small blocks (3-5): Rapid commits
- Strict QoI (0.2s): Only fresh data
